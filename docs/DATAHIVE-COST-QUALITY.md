## 结论

1. 调度方长会话确有大量累计 token，值得优先优化；但不能把其所有用量归因于审核，
   也不能把缓存输入按普通输入价格计算费用。
2. 独立验证确实发现了仓内测试未覆盖的产品缺陷。应保留这种验证，重点减少重复
   转述、重复模型审阅和无意义巡视，并将重要的独立检查提前到高风险任务。
3. DataHive 已发生一次 omp → Codex 调度方交接。值得把临时交接整理成可恢复的
   接班流程，但两任工作范围和阶段不同，无法证明换会话或换宿主带来多少节省。
4. 先补实际项目的计量闭环、明确验收职责和阶段接班，再逐步建设同伴消息。
   网状拓扑本身既不保证省 token，也不保证正确性。

## 工程质量：哪些机制有帮助，哪些增加返工

| 观察 | 证据与解释 | 对 kumi 的意义 |
|---|---|---|
| 全绿测试仍漏真实功能 | P5 作者 15 项任务的逐任务门禁通过，切片验证仍列出 16 条缺陷和 6 项证据范围问题；含 robots 未接线、续爬错误、CLI 配置无人读取 | 验收需要“规格声明→实际可观测行为”的映射，复跑作者测试不能替代 |
| 独立探针有增量价值 | 发布链验证真实运行 fuzz 后发现 CR-only robots 越界写；引擎验证自建请求日志、fixture、数据库/JSONL 对照 | 保留独立验证，优先投向边界、状态机、外部输入、跨层接线 |
| 验证装置也可能误导 | P5 第二轮验证发现自己的服务器记账时机导致请求漏计，修正装置后改变结论 | 验证者仍需负对照和证据；“新 agent”不是正确性保证 |
| 控制方也能制造问题 | 报告记载合并依赖未就绪、作者运行中合并、并发测试污染、一次修复引入活锁后回退 | 工具门槛同样约束控制方；高消耗不等于高可靠性 |
| 重要问题发现偏晚 | 单测把缺陷行为固化成期望；robots 接线后多项测试才暴露错误前提，后续多轮继续发现 CLI 接线与文档差异 | 高风险契约早验收，统一记录未覆盖项，避免每轮重新猎错 |
| 检查重复叠加 | 作者自测、控制方独立快照多预设、验证者新装置、控制方再复现、合并后全量；q1 计划有 19 条命令 | 明确每层检查的目的；可重放的确定性门禁少占模型上下文，按风险分配人工式审阅 |
| 长时间停滞未及早收敛 | 修复 v1 约 16 小时零提交后被收口，v2 也停滞；有原始未完成产物记录 | 引入进展检查点、预算、可靠停止和保留成果的接班，不把多开实例当解法 |

这些是该次运行中的机制观察，不能证明 kumi 导致了上述产品缺陷，也不能在没有
同任务对照时证明多 agent 的整体质量优于单 agent。模型、任务难度、测试设计和
操作者习惯都混在其中。

原报告还有两处不能直接沿用的强结论：

四类宿主已读模型字段为 `deepseek-flash` 或 `deepseek-v4-flash`。仅凭别名无法证明

## 新 agent 接替旧 agent：可以做，但要交接职责

DataHive 的真实交接证明“启动后继、读交接书、继续派单”有实际可行路径，尚未证明
自动交接中的崩溃恢复、监督连续性与成本优势。推荐把接班和独立验证分开设计：
新作者接替实现不自动成为独立验证者；验证者若修改被验收代码，应另外安排相应复验。

接班包应小而完整：目标与明确授权、spec/plan 版本、源码/未提交成果的精确位置、
已作决策及理由、验收证据与未覆盖项、运行中子任务和原生身份、未决审批、预算、
下一步及失败恢复办法。详细历史按需引用，不默认复制全部会话。

建议的交接步骤：

1. 在任务/轮次安全边界提出接班，固定交接版本。优先考虑已完成阶段、输入规模上升、
   反复压缩/遗忘或预算接近阈值；不把某个通用 token 数硬编码为所有宿主的阈值。
2. 后继先只读核对交接包、现场状态与权限范围，确认接班准备完成。旧控制方仍负责
   监督；不能在此时让两者同时驱动子 agent。
3. 旧方停止派单和输入；核对未完成副作用；释放/到期并完成显式控制权交接。
   后继获得自己的租约并接续观察，记录生效时点。旧方随后退出或保留只读。
4. 交接失败或双方崩溃时，从账本恢复；旧方不凭猜测重新开始输入，后继也不因
   收到交接文档就抢占活租约。未解决的审批、uncertain 提交和取消必须保留。

目前本地租约无法强制拦截直接终端输入，这仍是合作流程，不能宣称严格分布式排他。
长远需稳定的职责 ID 与实例代次；替换同一职责不应被建模为无限加深的子孙链，
也不能借“接班”绕过原有任务范围、预算或最大委派深度。
在已有明确授权与预算内可允许 agent 自行触发接班，不必每次等待用户点头；
不能自动继承超出原范围的宿主权限。

接班并非只能等网状通信完成后才做；它可以先基于已有文件、账本和显式输入交接演练。
作者更换原生实例时同样需要记录继任关系和新实例身份；旧轮结果保持不可变，
不能让新实例冒用旧实例的发布身份。具体沿用 job 的新轮还是建立关联的新 job，
需按现有资源绑定与取消状态确定，作为 CQ-03 设计项，不能直接绕过当前协议。
是否自动触发，应比较继续原会话、压缩后继续、精简交接新实例三种方式，计入交接
写入/读入、缓存变化、遗漏导致的返工、恢复时间和检出质量。
