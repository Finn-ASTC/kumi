## 1．这一阶段交付什么

交付同机、同 run、明确参与者之间的协作闭环：**发现同伴 → 正文落盘 → 短通知 →
接收方自主读或延期 → 工具到期跟进 → 必要回复/处置 → 原任务正确收尾。**
允许受控打断造成暂停，接收方检查并恢复；未读责任不靠会话记忆，也不把模型理解
当作工具能够证明的事实。日常发送、查询、提醒不要求调度模型转述或逐条审批。

第一版限制为单条消息一个精确接收方，支持明确的答复关联与话题；多收件方由调用方
分别创建有独立回执的消息。不做全员广播、跨机器 relay、任意读取其他 agent 会话，
也不把开 agent、切轮、批准操作、杀进程或改验收标准混入发消息工具。
网状是任何获准同伴可直接寻址，不要求全连接；角色不按宿主划等级。

最小成功例：作者忙于测试时收到验证者的接口问题，延期至当前测试结束或约定时间；
期间压缩/重启也能找回待办；到点查看并直接回复；作者仍通过原验收，调度方继续
自己的集成工作。若收不到、读不了或恢复受阻，明确留下负责人和异常。

## 3．分工与数据边界

| 层 | 拟承担的职责 | 不承担的职责 |
|---|---|---|
| 消息存储与状态 | 发布正文、精确路由、收件箱、读取/延期/处置、幂等操作 | 发键、模型判断、业务理解 |
| 提醒调度 | 查到期、合并提醒、冷却、次数/成本预算、超期升级、健康状态 | 接管终端输入权、自动批准、每次调用大模型 |
| 通知适配器 | 在已授权目标提交短通知，报告自己可证明的结果 | 清除 kumi 未读、自动转交新实例、决定业务完成 |
| 接收方 | 查原工作状态、读/延期、按任务范围回复、核查后续做 | 仅凭“收到”证明读全文，未知执行直接重放 |
| 监督负责人 | 处理无法投递、超期、无接管方和恢复受阻 | 逐条中转正常问答、重新审核全部正文 |
| 任务收尾 | 按契约核对本轮责任、固定截止水位、验收/交付 | 把通信 ACK 当验收，迟到消息修改旧 result |

实验模块按上述边界划分，拟使用 `messages.py`、`receipts.py`、`reminders.py`、
`notice_adapters.py`、`handoff.py` 和 `closure.py`；它们是计划中的文件名，不是已有 API。
首批可合并小模块，避免为每个状态建立一个服务。复用标准库和既有发布/锁工具。

### 最小记录

| 记录 | 必须表达的字段/事实 |
|---|---|
| 消息 | schema、message_id、operation_id、run、精确发/收地址、thread/reply_to、类型、优先级、短主题、创建时间、不可变正文摘要与长度 |
| 读取责任 | 消息/正文版本、责任人、已返回范围、接收方确认、最迟检查时间、检查点、原期限、延期次数/历史、解决要求、最终处置 |
| 通知尝试 | attempt_id、包含的消息/责任 revision、接收实例、适配器配置、输入所有者/代次、预检时间、提交结果、证据引用 |
| 恢复记录 | 通知/任务绑定、未决 tool/call 或执行句柄、原工作位置、无需恢复/接续/等待/未知、可回查证据 |
| 策略与健康 | 版本化时间/批量/容量预算、提醒进程身份与租约/心跳、到期游标、未知/降级原因 |
| 收口记录 | job/round、截止序号、责任 revision/摘要、结果/验收版本、豁免/转交、sealed/committed 或 aborted |

操作都有调用者身份和稳定 operation_id；同键同输入返回旧回执，同键不同输入报冲突。
消息 ID 是关联标识，不是授权凭据。正文或授权范围变更须新版本/新消息，旧读回执
不能覆盖新正文。短主题和路径引用均视为数据，限制长度、控制字符和可访问范围。
通信权限沿用合作 agent 的信任模型；共享用户目录不提供恶意进程隔离。

## 4．存储、并发与崩溃恢复

首版选择 run 内版本化文件 sidecar，保持正文落盘；不把 SQLite/hcom DB 设为唯一
事实来源，也不同时维护两套可独立写入的权威状态。具体目录名在 schema 实现时固定。

消息正文先作为不可变对象完整发布，再在**单次不可变操作事件**中同时登记消息和
初始读取责任；事件发布并同步目录后才返回入队成功。单一提交点避免出现“消息可见
但没有未读责任”。崩溃留下的未引用正文不投递；恢复按相同 operation_id 对账。
变更事件含递增序号、预期责任 revision、操作者和输入摘要；不改写既有事实。

同 run 变更复用 job 索引锁，成员替换、投递准备、责任变更与收口遵守统一锁顺序。
网络、模型和终端 I/O 不持有存储锁：锁内登记意图，锁外执行，回锁校验并记结果。
输入所有者按目标串行执行，交接期间保留未决尝试，不能因租约过期就重发不确定输入。
这是合作式排他；herdr/sendkey 不支持的外部原子条件不能靠一个字段补出来。

读视图提供分页与每接收方游标，摘要缓存可以重建，损坏不当作空收件箱。
初版允许有界重放事件；先测 10/100/1000 条消息的存储和读取开销，超过声明容量
显式拒收并让发送方留有失败待办，不截断或静默丢弃。缓存后续按测量优化，暂不承诺
常数复杂度。检测缺号/摘要变化/符号链接；人为删整个历史或整目录回滚不在首版保证内。

## 5．状态与工具动作

不要把所有事实塞进一条“已发→已读→完成”的线性状态：

| 维度 | 状态草案 | 允许推进的证据 |
|---|---|---|
| 投递 | queued / attempting / submitted / uncertain / rejected | 唯一执行方的适配器回执；submitted 不推导已读 |
| 读取 | unread / partial / body_returned，加独立 acknowledged 字段 | 按正文版本和范围返回内容；丢输出保留不确定，agent 确认仅为声明 |
| 安排 | ready / deferred / due / escalated | 固定策略、显式延期或时间/检查点；计时不消除读取责任 |
| 业务处置 | open / replied / resolved / dismissed / withdrawn / transferred | 与请求要求相符的回复/证据或获授权处置；回复不必然解决 |
| 恢复 | not_needed / resumed / awaiting_result / unknown | 与原工具/产物关联的检查结论，独立于消息状态 |

拟提供发送、摘要查询、正文分页读取、注意/读取确认、延期、回复、处置、到期查询、
恢复对账、责任转交等动作。确切 CLI 在实现时决定，本文不提供不可运行的示例命令。
发送者只能管理自己有权撤回的请求；接收者可标不适用并说明理由。涉及授权契约的
关键责任只能由相应负责人关闭/豁免，不能通过 dismiss、改优先级或发一个 ACK 绕过。

阅读不等于照做：消息不能覆盖用户指令或新增操作授权。正文可以先读、稍后处理；
完整正文返回且接收方显式确认后，可按契约解除读取待办，业务责任仍在。这仍是工具
事实加接收方声明，不是理解证明。文件读取 helper 不应在只返回摘要或截断内容时标
完整阅读，不能把 tool stdout 成功当成 agent 已理解。

### 轮次结束后的消息权限

现有 M0 的 `members.health()` 在任务有 result 后会返回 `round_finished_or_invalid`，
因此不能把“可接收新工作/输入”的资格直接复用为全部消息查询和处置权限。
M1 分开校验：新消息入队/通知仍要求当前精确实例满足相应条件；既有责任的历史读取、
恢复查询按精确旧地址和仍有效的访问授权提供，不能因 result 出现就变成不可见。
处置/交接必须由当前有权主体或明确获委派的监督方完成，过期 presence 本身不授予权限。

提交结果后的反馈若要求继续改代码，由控制方处置并进入明确的新轮；旧 result 保持
不可变。关闭/替换实例的迟到消息由监督方处理，不给旧 pane 再发输入，也不自动改投
同名新成员。批次 2/4 验证“有 result 但未 close”“已 close”“实例替换”三种状态下，
旧责任仍可审计并按现有授权处置，且不能借此恢复旧轮工作或绕过 seal。

## 6．延期、防遗忘与提醒服务

消息入队时就按策略确定初次检查时限和监督责任人，即使 agent 未回应也能进入到期
队列。延期必须提交 next_check_at；可附 checkpoint ID，任一先到即到期。重复延期
受累计预算和原期限约束，未给时间的“稍后”不构成成功延期。

时间参数分开：期望读取期限、业务答复期限、下一提醒时间和提交尝试超时不是同一个
时钟。持久记录绝对时间，同进程等候用单调时钟；重启重算，明显时钟跳变记异常，
不能倒拨时间后无限延长原期限。检查点必须绑定本轮标识，旧轮同名事件无效。

首个 sandbox 演练采用可配置的候选策略，**仅为测试参数，不是生产默认**：

| 参数 | 演练值/行为 | 验证目的 |
|---|---|---|
| 普通消息初次检查 | 120 秒；可用更早检查点 | 验证主动延期与时间兜底 |
| 高/低优先级初次检查 | 30/600 秒，仍受原期限约束 | 验证排序与防饥饿，不增加输入权限 |
| 延期上限 | 最多 2 次，累计不突破既定期限 | 验证反复延期升级 |
| 同目标提醒冷却 | 30 秒，合并最多 10 条摘要并暴露溢出计数 | 控制唤醒与上下文开销 |
| 追加提醒 | 首次提醒后最多再提醒 2 次，未处置则升级 | 不无限重试、不删 overdue |
| 进程健康 | 心跳 5 秒，15 秒未更新标记未知/离线 | 验证监督空窗可见；暂停时不用真实长等待 |

确定性测试注入时钟快速覆盖这些时限，不靠真实 sleep；原生实验再测实际调度抖动。
关键任务的期限由契约/负责人确定，发件者标高优先级不能单方面制造交付阻塞。

提醒器先实现一次可重入的 tick，再实现显式启动、带截止时间和健康文件的 run 内
循环；不自动安装系统守护进程。调度 agent 不必一直占着会话等待它，正常 tick 不调用
模型；只有异常需要 agent 判断。观察器读状态，执行器持输入权，二者职责可同进程实现。

提醒器崩溃后待办不丢，重启合并当前到期项，不补发过去每一次提醒。状态查询明确
显示是否有人监督；外层现有监督方跟进提醒器健康。如果监督方和提醒器都停止，系统
只能持久保留并在下次恢复报警，不能宣称仍按时唤醒。该限制要进入能力表和测试。

## 7．hcom 与原生通知的选择试验

候选通信后端与判定模型分开。hcom 先是可替换通知适配候选，不接管 kumi 正文、
责任账本、任务控制或审批。前次静态审阅固定于
`fabb309b57cb33b39c69b773cd759723a10e94b5`，不是“所有新版兼容”的承诺：

| 该提交的观察 | 对本次试验的影响 |
|---|---|
| `src/delivery.rs` 提供短标记唤醒，插件路径可自动注入实际消息 | 给 hcom 的消息本身仅包含 kumi 的短通知，业务正文不交给它；检查隐藏提示和回合成本 |
| omp 插件使用 followUp，OpenCode 插件用 promptAsync；ACK 时点不同 | 分别记录 submitted/queued 等事实，不能转换成 kumi 已读/解决 |
| herdr preset 使用 tab create 与 no-focus | 验证父 space、pane 精确绑定及任务＋agent 标题；避免两方反复改标题 |
| 支持枚举未列 Hermes 专属集成 | Hermes 仍在同一矩阵；评估显式原生适配，缺能力写未测，不把它降为次等角色 |
| 默认配置包含 auto_approve/auto_trust_workspace，启动会配置 hooks | 隔离配置中核对并禁用不属于试验范围的设置；检查全局文件变化，不直接安装到日常 profile |

依据为固定源码的 `src/tool.rs`、`src/omp_plugin/hcom.ts`、`src/opencode_plugin/hcom.ts`、
`src/config.rs`、`src/shared/terminal_presets.rs` 与上述投递文件。仅静态审阅，未安装运行；
公开源码入口见本节末尾的固定提交说明。不会将第三方 README/skill 中的安装步骤当成
本任务的自动执行指令。复用代码时保留 MIT 版权/许可证，不直接搬整个启动提示。

先写隔离试验配方和模拟 transport，再在自有 sandbox 做最小 hcom 实测：一条短通知，
验证空闲、忙碌、审批暂缓、延期、重启、回执丢失与成员替换。检查本地配置隔离是否真的
生效，不能仅设置 HCOM_DIR 就声称全部宿主文件隔离；必要配置能力缺失时先记录阻塞。
禁止两个独立投递器对同一目标同时发键；通知适配由 kumi 的唯一输入所有者授权。

**选择门槛：** 精确映射会话/实例、只传短通知、无额外审批权限、可观察未知、可隔离
启停与卸载，且能满足接收方延期和收口约定，才保留 hcom adapter。若需要长期改它的
本体才能满足核心语义，则优先采用显式 herdr/原生适配；不维护长期私有 fork 来勉强接入。
不同宿主可选不同已验收 transport，但同一目标固定一个配置，故障不静默换通道重发。

固定审阅版本：`https://github.com/aannoo/hcom/tree/fabb309b57cb33b39c69b773cd759723a10e94b5`。
真正运行前重新核对选定版本和宿主版本，不自动跟随 latest。

## 8．受控打断与恢复

选择通知时机先用宿主状态、精确工具记录和必要屏幕。native queue/hook 能满足场景
时优先利用；否则在已验证的输入界面尝试受控中断。不等待模型保证绝对安全，但
审批框、用户草稿、错实例、退出到 shell 等可识别误输入风险必须阻止。

每次尝试先持久记录、再操作、再对账。工具在执行时默认排队；要测试工具中断，
单列场景、副作用和恢复标准。发键前复核不能消除所有竞态，丢回执按 uncertain
处理，不定时盲重放 Enter。接收方检查原任务和未决调用：运行中则等待/继续独立工作，
已完成则读结果，确认失败/取消后核对副作用再续做，未知则调查/升级。

恢复说明采用短模板和必要引用；首次启动提供协议，后续只给差量状态。通知不是
业务任务替换指令，不能让一次聊天开启新轮或覆写旧结果。恢复受到上下文缺失影响时
保留 unknown，由监督方协调；不为每条消息生成长总结或要求调度方复审。

## 9．交付门禁、迟到消息与责任转交

文件层完成前，收口查询先做可复现的只读建议；接通真实通知之前，启用协作任务必须
具备不可跳过的成功收口检查。不能只靠 agent 自愿执行一个可选 wrapper。
代码落点是 `jobs.py` 的 completed close/成功轮次 activate 与 `completion.py` 的 readiness
摘要，兼顾 `round_history.py` 历史事实；具体小补丁在实验分支实现，不从运行脚本 import
`experiments/`。未启用协作的 v1 任务行为不变；启用但不认识版本/缺配置时明确拒绝。

拟采用可恢复 seal：

1. 控制方准备交付时，在 job 索引锁内检查责任 revision，发布本轮 seal 和接收截止序号。
   seal 后新消息必须明确退回或进入可见的 late 队列；不静默计入已经检查的集合。
2. 核对 seal 内全部相关责任。关键项必须达到契约要求的已读/解决或有授权豁免；
   普通信息至少明确处置；有业务回复要求时“读过”不够。无故批量归档不能绕过关键项。
3. close/activate 重新验证 seal、正文/结果/验收绑定和责任 revision，再记录本轮成功
   结论/切轮。新未决控制或状态变化使检查失效，不能只信之前的 ready=true。
4. seal 后崩溃、job 保存成功但消息侧完成回执失败，都可按 operation_id 对账；
   明确记录 pending/committed/aborted。解除 seal 是显式操作，不能因超时自动撤销后
   让过期的收口请求继续成功。late 队列由负责人处置或进入新轮，不修改旧 result。

seal、发送、处置和 job mutation 在同一协调锁顺序下检查；跨文件仍不是事务，
实现须用崩溃注入证明每个发布边界可恢复。不能实现该保证前，不把可选预检宣传成门禁。
failed/cancelled 收尾也要输出未决责任与负责人，但不因普通消息阻止必要的停止操作。
历史补记验收保留当时覆盖事实，不能用后来的已读回执证明过去已满足门槛。

接班/替换成员时，旧实例不再收到新输入，旧责任转为待接管。转交绑定旧新地址、范围、
未读/未处理水位与原期限，新方确认后才完成交接；未确认仍由原监督负责人兜底。
原消息保持指向旧实例，转交记录明确关联，不能按“最新同名 agent”重定向。

UX-02 的历史分组/原生归档须读取同一未决责任与接管事实，不通过折叠或归档清空
消息待办。原生会话定位是消息地址的关联记录，不替换 run/member/instance/job/round；
恢复旧原生会话也不能复活已关闭轮次。归档引起证据路径变化时仍保留验收和计量来源。

## 11．测试、真实实验与成本

协议故障测试包括：同键同/异正文、并发发送与回复、错误实例/轮次、被替换成员、
读取分页与输出丢失、正文篡改、检查点永不来、时钟跳变、两次延期后再延期、
提醒器/接收方崩溃、lease 交接、合并提醒期间新消息、预算耗尽、无人接管与 seal 竞态，
以及结果发布/关闭/成员替换后历史读取、处置和新输入资格的差异。
“已处理”伪回执和已读但未答复必须作为负例。

先两方机械消息验证，再做调度方＋作者＋验证者的固定小项目。作者有一个可复现的
缺陷，验证者直接反馈，调度方同时做独立集成检查。测试中安排需要延期的通知、
迟到工具结果、一次接收方重启和交付前关键消息；保留失败与修复后的复验。
轮换角色和异构组合；全宿主均列入契约，不因 transport 差异改变角色权限。

对照固定任务/spec/oracle、种子、模型配置、预算和版本，分开比较：
显式转述 vs 文件消息＋状态通知；后者 vs 加模型选时。每个已选组合至少重复 3 次
寻找不稳定因素，样本仍不足以证明普遍可靠；更大效果评估再按观察误差扩样。
只在相同质量门槛下比较成本，调度方未逐条转述、仍有独立工作进展需有时间/任务证据。

计量至少包括调度/作者/验证者、后端判定、提醒唤醒、恢复、失败重试；额外提示/token
也算成本。记录已知用量与未知覆盖，不把短通知字符数直接当节省 token。
时间分入队、通知提交、注意、正文返回、回复/解决与原任务恢复；主动延期单列，
只对有完整时间的样本报分位数并说明数量。关键质量指标：错投、误审批、重复副作用、
丢未读责任、逾期/无负责人、原任务验收与监督空窗，不用“所有消息都标已读”替代。

## 12．审批、网状扩展与发布

报告审计后再确定审批模型下一候选；DeepSeek 报告配置、Jev、本地服务均保持可替换。
logprobs 和流式属于适配能力，不能代替授权检查和校准；不直接采用 0.05 或跨模型
共同阈值。通知候选与 `allow/deny/escalate` 使用不同标签和版本，不把判断混成一个分数。
真正审批按统一操作身份/期限 → 持久队列 → 协作者 → 必要人类窗口 → 原生执行回执
推进；与本轮未读提醒可以共用调度模式，但记录和权限独立。

M1 通过后依次做：M2 作者↔验证者的有界返工协作；M3 跨模块依赖、接口决定和循环
等待处理；CQ-03 显式接班；最后再评估更自主的协调。原验收快照、写入所有权、取消
与审批边界继续保留，接班不依赖无限增加 agent 深度。B 的 30 秒审批响应和计量缺口
单独跟进，消息实验通过不关闭它们。

发布前分别检查：不启用消息的旧任务回归；启用任务缺配置/服务的失败路径；最小
运行包与离线安装；可选插件全局变更/卸载；MIT 归属；关闭功能后的未读责任处理。
关闭提醒不自动清空责任；已启用的任务需完成显式处置/交接才能退回旧路径。
只有 runtime helper、短协议与必要参考进入六个 skills，runner、评测数据和原始日志
留在开发/实验目录。通过的组合可选择性合并，未测组合明确禁用自动投递；不自动推送、
安装个人配置或改默认值。

每批结束更新本文状态表、实际证据与下一批入口。参数变动需标明是测量结果还是
实验选择，避免再积累互相矛盾的“下一步”段落。
