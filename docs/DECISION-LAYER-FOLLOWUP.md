## 本次确认的方向

用户明确：安全打断不能完全保证，更重要的是约定好通知方式；agent 被打断、收到
通知并唤醒后，自行检查是否需要恢复原工作。目标调整为**尽量选择合适时机、允许
工作中断、支持有证据的恢复**。不等待模型证明“绝对安全”才开始验证消息通道，
也不以零中断作为验收标准。状态判断用于减少干扰，恢复协议承担中断后的接续。

- 正文先落盘，终端仅通知发送方、优先级、短主题和消息 ID；发送方随后继续工作。
- 接收方先检查刚才的工作状态，再选择立即读、持久延期、恢复原工作或请求帮助。
- 通知并不要求立即答复，也不授予执行、审批或修改任务范围的权限。
- 打断可能使结果缺失或工作暂停；恢复前先核查实际执行状态，不直接重跑上一条命令。
- 已知审批/选择器、错误实例、已退出到 shell、未处置输入草稿等仍阻止普通通知输入。
  这些是可识别的误输入风险，与是否能完全证明业务工作不中断分别处理。
- 四宿主/五配置共用语义。原生差异留在适配器，不把 Codex/omp 设为特殊角色。

## 职责分工与最小恢复约定

| 负责方 | 要做的事 | 留下的事实 |
|---|---|---|
| 发送方 | 用稳定消息 ID 保存正文/范围/优先级/期限，继续自己的工作；阻塞才登记依赖 | 文件发布结果、目标实例、问题/回复关联；未知不能声称已送达 |
| 输入执行方 | 单一所有者串行协调审批与通知；观察、选时、必要时中断、确认输入就绪、提交短通知 | 精确实例/轮次、观察时间与来源、通知尝试、提交或不确定回执 |
| 接收方 | 检查原任务进度和未决执行；按优先级自主读取/延期，核查结果后续做 | 最小恢复结论、必要的证据引用、消息处理安排；不要求逐条聊天回复“收到” |
| 监督负责人 | 关注投递失败、恢复受阻、消息期限和输入执行方健康 | 负责人、下一检查点与升级原因；调度方同时继续独立工作 |

接收方启动任务时获得短协议，不要求每轮加载本报告或完整会话。检查按需进行：

1. 辨认此次通知及当前 job/round，确认原任务是否仍活动。已交付/取消/换轮的工作，
   按既有门槛交给控制方处理，不能借通知继续改旧结果。
2. 从当前上下文与最近检查点定位正在做的步骤。必要时读取关联 tool/call ID、
   进程/任务句柄、输出游标和产物证据；这些只收集实际可得项，缺失明确记 unknown。
3. 对未决动作分类：仍在运行则关联并等待/继续独立工作；已完成则读回结果；
   已确认取消/失败则核对副作用后决定续做；状态未知则先调查或请求帮助。
4. 根据原授权、幂等性和检查结果决定是否重试。缺回包、日志没有配对结果、通知
   中断回执都不能单独证明操作没执行；不能重复启动后台任务或重复发布产物。
5. 自主读消息或持久延期，再继续原任务或在既有范围内调整。恢复受阻时暴露待核查
   事项与负责人，不自行新建替代 agent 来掩盖未知。

最小恢复结论只记录 `无需恢复 / 已接续 / 等待执行结果 / 状态未知需核查` 等事实及
引用，不强制每次写长总结、复制历史或额外调用调度模型。状态名是设计草案，schema
在 M1a 固定。观察器可记录机械信息，不能假装它知道 agent 全部内部思考。

## 通知时机与错误恢复

先采用宿主状态、按调用 ID 配对的工具记录和必要屏幕信号。没有工具记录只说明
“未观察到”，不自动得到安全结论；也不要求工具日志全知才能试验已经验证的宿主
中断路径。候选输出使用 `可尝试通知 / 等待 / 状态未知` 及理由、来源和有效时间，
不称为安全保证。若新状态出现则重新判断，不能一直复用过期的“可通知”。

优先原生排队/steering 或空闲输入；具体通道依对应配置验证。需要打断时，在预先
约定的通知/恢复策略和预算内，由唯一输入方操作，并确认 agent 已进入正确输入界面。
已知前台工具执行时默认等待；如实验需要在此状态打断，须单列宿主取消语义与副作用
恢复场景，不能仅凭消息“高优先级”越过。期限到达只触发升级/重新安排，不授权盲发。

发键前重新核对身份、控制权、状态/版本，降低观察到输入之间的竞态；这种复核不等于
终端具有原子的比较并交换（CAS）。前后证据不一致或回执丢失时保留 uncertain，先核查
是否已经提交/读取，避免重复回车。一次通知中断不代表整个 job/后台任务已停止，
不复用 `controls.py` 的 stopped 结论，也不降低现有取消门槛。

消息状态与通知尝试分别记录：保存、通知提交/不确定、已注意、正文已读、延期、回复、
问题解决不是单一线性状态。接收方主动读取可以早于终端通知；读过可再延期；恢复
状态也不能冒充消息已处理。合并积压、按稳定 ID 去重，设置提醒/中断预算；明确延期
后只在约定检查点或优先级/期限有实质变化时提醒，避免反复唤醒。

## 验证矩阵与指标

Codex、omp、Hermes、OpenCode OMO/pure 每格写通过/失败/未测及版本/配置，不能用 omp
报告替代其他宿主结果。首轮采用相同契约，按实际可用配置分批；不预设特权宿主。

必测场景：思考/输出文字中收到通知；工具正在执行；工具实际完成但结果晚到/丢失；
中断后后台仍运行；审批/选择器/草稿输入保护；两个发送方合并通知；重复/旧实例消息；
已读与延期后继续原任务；通知后接收方或投递器崩溃；部分提交不确定；取消/交付后消息。
缺上下文时也应暴露恢复受阻并核查，不能靠重放副作用过关。

记录四段时延：入队→通知提交→接收方注意/读取→回复/解决；另记原工作恢复时间，
区分主动延期与投递故障。统计模型/读屏次数、观察耗时、额外唤醒与恢复 token、未知
用量、中断次数、重复副作用、原任务验收和监督缺口。小模型的首块/完整判定/总调用
耗时分别计，不用首块代替完整可用决定。

合并条件是已支持场景中目标正确、无误审批、消息可恢复、原任务最终通过原验收，
未知结果不盲重跑、延期按约定回看；同时公开覆盖缺口。允许可解释的暂停和恢复成本，
不承诺无损或零中断。存在已知错投/重复副作用则保留失败、修复重验，不发布该路径。

## 可替换判定后端的安排

保留已实现的[通用影子接口](APPROVAL-SHADOW.md)。审批和通知时机共用适配器管理、
预算和错误记录思路，但任务契约、标签、提示、校准和门槛分别版本化；不把通知候选
硬塞进 `allow/deny/escalate` 的审批结果，也不在本轮假称新增了通用 judge API。

OpenAI 兼容 chat、logprobs、stream 是未来某类适配器的可探测能力，不是所有后端的
强制接口；Jev、规则和本地分类器仍可用自身结果。能力探针本身可能外发/计费，应显式
执行并计入预算，不作为无感启动动作。端点兼容不意味着模型/分数质量等价。
不固定跨模型阈值，不静默换供应商，缺分数也不伪造概率。审批失败先升级复核，
保留既定“协作者能处理则处理、确需用户时才弹人”的目标，不直接将所有异常弹给用户。
